## 1. 一句话结论

KFF-B01-NEW-01 **FIXED**：Guardian 现在有**按阶段计时的 bounded liveness**。子进程在 `ready` / `start` / `context-opened` / `before-submit` / 提交后的任一阶段永久无进展时，父进程会在该阶段的预算耗尽后**先请它收尾、再强制结束整棵进程树**，写出只包含"父进程确知事实"的 `kff.guardian-closure-no-progress.v1` 记录，让 `runGuardian` settle → `finally` → flush journal → command 收口 → execution slot 释放；**旧 command 零重放**，业务结果不确定时保持 `UNKNOWN` + quarantine，第二合法 command 能被真实执行。旧行为（`Promise.reject(TimeoutError)` 或干脆永不 settle、child 留在后台）已被确定性 RED 钉住并转绿。

B01 在 `B01-state-transition.md` §10c 明确留下的那句"**本轮修复覆盖不到，需规划端裁定**"，就是本轮的输入；本轮把它关闭。

## 3. 缺陷与修复

**KFF-B01-NEW-01**：child 被 spawn、发过 `ready`、收过 `start`，然后卡住——`error` / `exit` / `close` / IPC 一个都不来 → `runGuardian` 永不 settle → `main.ts` 的 `finally` 永不执行 → flush 永不执行 → command 停在 `CLAIMED`、`quiesced_at IS NULL`、`action_single_execution_slot` 永久占用，重启不自愈。

修复的五个组成部分（详见 `B01.1-state-machine.md`）：

1. **阶段化看门狗**（`awaiting-ready` / `awaiting-start` / `awaiting-context` / `awaiting-intent` / `granting` / `submitting` + `grace` / `force`）：阶段是**父进程已观察到的事实**，每次有效 progress 只刷新对应阶段的预算；预算可配置（`hooks.liveness` > 环境变量 > 生产默认），测试用毫秒级值，生产默认 30 s / 30 s / 120 s / 900 s / 60 s / 300 s。
2. **终止阶梯**：`stop` → grace（等它自己写真实 closure，那份证明永远优先）→ `terminateProcessTree`（Windows：`taskkill /T /F`）→ 再等 force → 无论如何都 **settle**。
3. **诚实的终止记录**：`kff.guardian-closure-no-progress.v1` 只带 `phase` / `process_terminated` / `context_opened` / `submission_state` / `forced` / `waited_ms` / `grace_ms` / `result`，**没有 `context_closed` 字段**，也无法被当作关闭证明读回（`readClosure` 抛 `GUARDIAN_UNCONFIRMED`）。
4. **结果映射拒绝伪造**：只有"从未到达 `ready`"才写 `CANCELED`；`submitting` 写 `UNKNOWN_OUTCOME`；其余写 `NEEDS_HUMAN`。没有任何阶段被统一写成 `GUARDIAN_STARTUP_FAILED` 或 `CANCELED`。
5. **隔离而不是错误释放**：`GUARDIAN_NO_PROGRESS` 进入 `acceptReport` 的 quarantine 判定 → environment `QUARANTINED`、lease `quarantined=true`、run/task `NEEDS_HUMAN`；`browser_status` 只有在 v1 证明下才可能变 `CLOSED`（终止不投影关闭）。

**Q1 BASE SHA？**

**Q3 KFF-B01-NEW-01 是否 FIXED？**
**FIXED**。定义：无进展的 child 不再让 `runGuardian` 永久 pending；终止被证明（`process_terminated`），记录诚实（无 `context_closed`），生命周期收口（DONE + quiesced），slot 释放，旧命令零重放，不确定结果保持隔离。

**Q4 deterministic hang 是否先 RED 后 GREEN？**
**是**，同一批 8 个用例：RED（HEAD 的 guardian + 记录在案的 arming shim）unit 6/6 超时（各 12 s）、integration 2/2 失败（91 966 ms 超时；64 650 ms 断言失败）→ GREEN unit 6/6（19.06 s）、integration 2/2（7 908 / 7 409 ms）。日志：`b01.1-red.log` / `b01.1-green.log`。

**Q5 watchdog 是否 phase-aware？**
**是**。6 个阶段 + grace/force，各自独立预算，progress 只刷新对应阶段；tick 跟随最短预算；预算三层可配置；测试值（毫秒级）与生产默认（30 s–900 s）分离。

**Q6 timeout 后 Guardian PID 是否消失？**
**是**，逐例以 `isProcessAlive` 轮询断言（unit `eventuallyGone`，integration `expect.poll`）。

**Q7 是否存在 descendant 残留？**
**未观察到**。真实两级进程树实测证明 `child.kill()` 会留下孙进程、`terminateProcessTree` 不会；真实浏览器场景（`guardian-recovery` 场景 2）恢复后 `nothingLeftRunning(root)` 为空，且该扫描先用一个见证进程证明它"看得见进程"。

**Q8 是否产生 submit permission？**
**没有**。watchdog 触发后 `submit-granted` 永不发出（用例 5 断言 `intentRequested === false`；`granting` 阶段的用例断言 `submission_state: 'UNKNOWN'` 而非"已提交"）。

**Q9 不同阶段 timeout 分别得到什么状态？**
映射表见 `B01.1-state-machine.md` §3：`awaiting-ready` → `CANCELED`；`awaiting-start` / `awaiting-context` / `awaiting-intent` → `NEEDS_HUMAN`；`granting` → `NEEDS_HUMAN` + `submission_state: UNKNOWN`；`submitting` → `UNKNOWN_OUTCOME` + `UNKNOWN`；进程未被证明死亡 → `NEEDS_HUMAN`。**没有任何阶段被统一写成 `GUARDIAN_STARTUP_FAILED` 或 `CANCELED`。**

**Q10 UNKNOWN 是否仍保持 quarantine？**
**是**。`UNKNOWN_OUTCOME` 与 `GUARDIAN_NO_PROGRESS` 都进入 quarantine 判定：environment `QUARANTINED`、lease `quarantined=true`（holder 保留）、run/task `NEEDS_HUMAN`。对照用例证明：同样报 `NEEDS_HUMAN` 但不带该事实时，环境回到 `IDLE`、lease 不隔离。

**Q11 Command 1 是否零重放？**
**是**。1 条 attempt、1 条 `action.reported`、1 条 command；恢复只写事实，从不 INSERT 新 attempt、从不重发平台动作；旧 command 已在终态，永不重新执行。

**Q12 execution slot 是否释放？**
**是**。命令 `DONE` + `quiesced_at`；该 agent 无 `READY`/`CLAIMED` 残留（无索引绕过、无删记录）。

**Q13 Command 2 是否真正执行成功？**
**是**。`guardian-recovery` 场景 2：slot 释放后新命令被真实 claim、真实读页、`VERIFIED_SUCCEEDED`、`state='DONE'`、`quiesced_at` 非空、`context_closed: true`、`commands/<id>/context-opened` 确实出现，且旧命令的 claim/report 各恰好 1 次。

**Q14 B01 的 002/003/004 是否全部未回归？**
