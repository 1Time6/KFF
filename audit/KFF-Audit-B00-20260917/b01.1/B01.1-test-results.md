## 1. 确定性复现：RED → GREEN（同一批用例，同一台机器）

RED 变体：把 `apps/agent/src/guardian.ts` 换回 HEAD 版本（sha256 `78c0c993…79bf1`，无任何 liveness/watchdog），**只**补 3 段与存活判定无关的 fixture arming（`guardianHangPoints` / `insideAgentProcessTests` / `guardianHangInjection` 与把点写进 child 环境的两行），因为 child 的环境是白名单、arming 本身位于被回退的文件里。child、协议、journal、控制端都是修复后的同一份。

| 用例（阶段） | 层级 | 每例 deadline | RED | GREEN |
| --- | --- | ---: | --- | --- |
| `awaiting-ready`（`before-ready`） | unit | 12 000 ms | **12 012 ms 超时** | 5 082 ms 通过 |
| `awaiting-start`（`before-start-ack`） | unit | 12 000 ms | **12 011 ms 超时** | 2 862 ms |
| `awaiting-context`（`after-start`） | unit | 12 000 ms | **12 012 ms 超时** | 2 988 ms |
| `granting`（`before-grant`） | unit | 12 000 ms | **12 001 ms 超时** | 2 771 ms |
| `submitting`（`after-grant`） | unit | 12 000 ms | **12 002 ms 超时** | 2 762 ms |
| 干净 stop 时优先真实 closure | unit | 12 000 ms | **12 001 ms 超时** | 1 914 ms |
| `granting` + 真实浏览器 + 已持久化提交意图 | integration | 90 000 ms | **91 966 ms 测试超时** | 7 908 ms |
| `awaiting-intent` + 真实浏览器被冻结 | integration | 90 000 ms | **64 650 ms 断言失败** | 7 409 ms |

汇总：unit RED 6/6 失败（72.05 s）→ GREEN 6/6 通过（19.06 s）；integration RED 2/2 失败（161.15 s）→ GREEN 2/2 通过（17.33 s）。

**第 8 行 RED 的准确含义（不夸大）**：该用例的停滞由 fixture 的 60 秒上界（`hangFrozen(60000)`）自行解冻，所以它没有像其他用例那样挂到 deadline，而是在 64.65 s 时以"子进程自己写出的 v1 closure"（`duration_ms: 60792`、`CANCELED` / `STOP_REQUESTED` / step `prepare`）resolve，从而断言失败。也就是说：修复前的父进程对"无进展"**没有任何贡献**，唯一的出路来自子进程的自我上界；子进程若不自限，父进程会永远 pending——这正是其余 7 个用例表现出来的形态。

**第 8 行的 shim 说明（诚实边界）**：这一行的 RED 无法只靠回退父进程得到，因为 arming 就在父进程文件里（这也是"生产无法意外触发"的结构性保证之一）。第一次不加 shim 的集成 RED（`b01.1-integration-red.log`）中，该用例根本没有停滞，直接以 `VERIFIED_SUCCEEDED` 完成——这恰好反向证明了封印有效。加上 shim 后才得到上表的 RED。该行的 GREEN 不需要 shim 之外的任何东西。

RED 中没有出现"偶发"：8/8 每次都失败，且失败形态与其阶段一一对应（无进展 → 永不 settle / 断言没有 `GUARDIAN_NO_PROGRESS`）。

## 3. Command 1 / Command 2 验收（§六）

`tests/integration/guardian-recovery.test.ts` 场景 2（本轮实测 18 443 ms，通过）：

- 先证明"检查本身看得见进程"：一个带 runtime 目录参数的见证进程能被扫描到，结束后从扫描中消失；
- Command 1：真实 guardian 在真实导航里停滞（`context-opened` 已发出），watchdog 在 4 s 预算上触发，**恢复耗时 < 14 000 ms**（远早于 child 自己的 15 s 导航上界 → 结束它的是 watchdog，不是 child 的超时）；
- Command 1 的终态：`agent_commands.state='DONE'` + `quiesced_at` 非空；`actions` 只有 1 条 attempt、1 条 `action.reported`；`commands/<id>` 的端点序列恰好是 `context-opened, status, quiescence`（**没有**第二次 claim、没有 resend）；
- 残留检查：`isProcessAlive(guardian_pid) === false`，且 `nothingLeftRunning(root)` 为空（真实浏览器也在内）；
- Command 2：slot 释放后新命令被真实 claim，真实读页，`VERIFIED_SUCCEEDED`，`state='DONE'`、`quiesced_at` 非空、`context_closed: true`、`commands/<two>/context-opened` 确实出现，且 `h.claimed.filter(id => id === one).length === 1`（旧命令零重放）。

`browser-message` 用例 4 的尾段补充：终止后的环境隔离是**由事实驱动**的——同样报 `NEEDS_HUMAN` 但不带 `GUARDIAN_NO_PROGRESS` 事实时，环境回到 `IDLE`、lease 不隔离；带该事实时才隔离。

## 5. Windows 进程树实测（§八，不依据文档推断）

`tests/unit/process-tree.test.ts`（3/3，714 ms）用真实的两级 node 进程树测量：

| 观察 | 结果 |
| --- | --- |
| 只 `child.kill()` | 直接子进程消失，**孙进程仍存活** → 仅杀 guardian 不足以终止它启动的浏览器 |
| `terminateProcessTree(pid)` | 父子两级都消失（Windows 走 `taskkill /PID <pid> /T /F`） |
| `isProcessAlive` | 对已回收 pid / 从未存在的 pid 返回 false 且不抛错 |

本轮顺带修掉一个与 `FORCE_COLOR` 有关的测试环境坑：该 shell 导出了 `FORCE_COLOR=3`，子进程会把自己的 pid 输出染色，导致 `^(\d+)` 匹配失败、用例挂到超时。已通过在 spawn 时设置 `NO_COLOR=1` / `FORCE_COLOR=0` 并在解析前剥离 ANSI 解决（在 `FORCE_COLOR=3` 下复测 714 ms 通过）。这是**测试自身**的缺陷，不是产品缺陷。
