# B01.1 状态机（Guardian 无进展终止与恢复）

本轮只处理 **KFF-B01-NEW-01**。本文只描述本轮真正实现并在测试中被观察到的状态与迁移；没有实现的语义不写进来。

---

## 1. 阶段（phase）的定义

阶段是 **父进程已经观察到的事实**，不是子进程正在做什么。它只在前缀进程真正收到对应消息时前进，因此每个阶段都是一条可被日志证明的边界。

```
guardianLivenessPhases = ['awaiting-ready', 'awaiting-start', 'awaiting-context',
                          'awaiting-intent', 'granting', 'submitting']
```

| 阶段 | 进入条件（父进程观察到） | 这一阶段覆盖的真实工作 | 生产预算 (ms) | 环境变量 |
| --- | --- | --- | ---: | --- |
| `awaiting-ready` | `runGuardian` 启动，child 已 spawn | 解释器启动 + child 模块加载 | 30 000 | `KFF_GUARDIAN_AWAITING_READY_MS` |
| `awaiting-start` | 收到 `ready`，父进程随即发出 `start` | child 解析 `start` 并开始准备 | 30 000 | `KFF_GUARDIAN_AWAITING_START_MS` |
| `awaiting-context` | 收到 `started` | 浏览器/上下文启动（child 自限 20 s） | 120 000 | `KFF_GUARDIAN_AWAITING_CONTEXT_MS` |
| `awaiting-intent` | 收到 `context-opened` | executor 全程直到提交边界（含长滚动读页） | 900 000 | `KFF_GUARDIAN_AWAITING_INTENT_MS` |
| `granting` | 收到 `before-submit`，父进程在跑 `hooks.beforeSubmit()` | 一次控制端调用 | 60 000 | `KFF_GUARDIAN_GRANTING_MS` |
| `submitting` | `beforeSubmit` 返回且未中止，父进程发出 `submit-granted` | 平台写入 + 回执确认 | 300 000 | `KFF_GUARDIAN_SUBMITTING_MS` |
| —（终止宽限） | watchdog 触发，已发出 `stop` | child 自己收尾并写证明 | 15 000 | `KFF_GUARDIAN_GRACE_MS` |
| —（强杀等待） | `terminateProcessTree` 之后 | 观察进程真正消失 | 10 000 | `KFF_GUARDIAN_FORCE_MS` |

要点：

- **每次有效 progress 只刷新它进入的那个阶段**（`phaseSince = Date.now()`）；慢的浏览器启动不会花掉 executor 的预算，反之亦然。
- 预算可配置三层：`hooks.liveness`（显式覆盖）> 环境变量 > 生产默认。非法值（非正安全整数）被忽略而不是被采用。
- tick = `max(20, min(1000, floor(min(阶段预算)/4)))`：最短预算决定采样频率，避免"预算 1.5 s、采样 5 s"这种失效。
- `awaiting-intent` 的 900 000 ms 是本轮选择的**生产**默认值（一次长读页不应误判）。测试通过 `hooks.liveness` 传 1 500 ms，几十毫秒级的测试值**没有**写进生产默认。

### 阶段迁移图

```
spawn ──► awaiting-ready
             │ ready 收到 → 父进程发 start
             ▼
        awaiting-start
             │ started 收到
             ▼
       awaiting-context
             │ context-opened 收到
             ▼
        awaiting-intent ─────────────┐
             │ before-submit 收到    │ 只在 awaiting-start / awaiting-context 时
             ▼                       │ 才前进（重复的 context-opened 不重置阶段）
         granting                    │
             │ beforeSubmit() 返回且未触发 watchdog、未 abort
             ▼
        submitting
             │ child 写 closure
             ▼
        settle（resolve 真实 closure）
```

## 2. watchdog 触发后的 12 项职责

`watchdogFired = true` 之后调用 `terminate()`。逐条对照实现位置：

| # | 职责 | 实现 |
| --- | --- | --- |
| 1 | 标记 watchdog 已触发 | `watchdogFired = true`（`setInterval` 内，且 `if (settled \|\| watchdogFired) return` 保证只触发一次） |
| 2 | 阻止任何新的 submit permission | 收到 `before-submit` 时 `if (submitted \|\| watchdogFired \|\| aborted) { stop(); return; }`；`beforeSubmit` 返回后 `if (aborted \|\| watchdogFired) stop(); else 发 submit-granted`。触发后**永不**发 `submit-granted` |
| 3 | 请求 child 正常终止 | `send({type:'stop'})` |
| 4 | 超过 termination grace 后强制结束 | `terminateProcessTree(child.pid)`；`forced = true` |
| 5 | 确认 guardian process 已终止 | `settleTerminal(!isProcessAlive(child.pid))` → 记录 `process_terminated` |
| 6 | 检查残留 descendant / browser | 见 §5（Windows 实测） |
| 7 | 持久化终止事实 | `saveNoProgress(runtime, …)` 写 `<runtime>/agent/closures/<command_id>.json` |
| 8 | 让 `runGuardian` settle | `throw recordNoProgress(...)` → Promise reject `GUARDIAN_NO_PROGRESS`；若 child 在宽限期内写出真实 closure，则 resolve 该 closure |
| 9 | 进入 finally | `main.ts` 的 `finally { clearInterval(timer); executionControl = null; await flushJournal().catch(...) }`（B01 已建立，本轮未改） |
| 10 | flush journal | `flushActionJournal` → `maintainActionJournal` → 读 closure 证据 → `action-reports` → `commands/<id>/quiescence` |
| 11 | 结束 command 生命周期 | `recordQuiescence` 置 `agent_commands.state='DONE'`、`quiesced_at=now()` |
| 12 | 释放 execution slot | 命令不再是 `READY/CLAIMED`，slot 可被下一条命令 claim |

终止阶梯（顺序不可交换）：

```
watchdog 触发
  → send stop → waitForTerminal(grace=15s)       // 仍然挂着的 child 也可能写出更好的证明
  → forced=true → terminateProcessTree(pid) → waitForTerminal(force=10s)
  → settleTerminal(!isProcessAlive(pid))          // 即使没有任何事件，也必须 settle
```

关键设计：**先礼后兵**。仅仅卡住但还能应答的 child，有机会关闭上下文并写自己的 `kff.guardian-closure.v1`——那份证明永远优于父进程写的终止记录，所以父进程会等它，而不是立刻写 `NO_PROGRESS`。只有宽限期过后仍无回应的 child 才被结束。

`settleTerminal` 的判定顺序（真实证据优先）：

1. `readClosureEvidence` 存在 → resolve 该 closure（真证明胜过父进程的记录）；
2. `watchdogFired` → `recordNoProgress(processTerminated)`；
3. 未 `started`/`submitted`/`contextOpened` → B01 的 `GUARDIAN_STARTUP_FAILED`（startup-failed 记录）；
4. 否则 → `GUARDIAN_UNCONFIRMED`（保持隔离，绝不伪造 CANCELED）。

## 3. `recordNoProgress` 的结果映射

```
neverReachedExecutor = phase === 'awaiting-ready' && !started && !submitted && !contextOpened
outcome              = !processTerminated ? NEEDS_HUMAN
                     : phase === 'submitting' ? UNKNOWN_OUTCOME
                     : neverReachedExecutor   ? CANCELED
                     : NEEDS_HUMAN
submission_state     = (phase === 'granting' || phase === 'submitting') ? UNKNOWN : NOT_SUBMITTED
```

| 阶段 | `process_terminated` | `context_opened` | `submission_state` | outcome | error_code |
| --- | --- | --- | --- | --- | --- |
| `awaiting-ready` | true | false | NOT_SUBMITTED | **CANCELED** | GUARDIAN_NO_PROGRESS |
| `awaiting-start` | true | false | NOT_SUBMITTED | NEEDS_HUMAN | GUARDIAN_NO_PROGRESS |
| `awaiting-context` | true | false | NOT_SUBMITTED | NEEDS_HUMAN | GUARDIAN_NO_PROGRESS |
| `awaiting-intent` | true | **true** | NOT_SUBMITTED | NEEDS_HUMAN | GUARDIAN_NO_PROGRESS |
| `granting` | true | 视观察 | UNKNOWN | NEEDS_HUMAN | GUARDIAN_NO_PROGRESS |
| `submitting` | true | 视观察 | UNKNOWN | **UNKNOWN_OUTCOME** | GUARDIAN_NO_PROGRESS |
| 任意阶段 | **false** | 视观察 | 视阶段 | NEEDS_HUMAN | GUARDIAN_NO_PROGRESS |

**唯一被写成 CANCELED 的情形**是"从未到达过 `ready`"——父进程没发过 `start`，executor 不可能被触及，上下文与提交都无从谈起，这是日志本身就能证明的事。其余任何阶段都不得写成 CANCELED。**没有**任何阶段被统一写成 `GUARDIAN_STARTUP_FAILED`。

## 4. 三个不同的事实（本轮不得合并的语义）

| 事实 | 字段 | 含义 | 不能推出 |
| --- | --- | --- | --- |
| 进程已终止 | `process_terminated: boolean` | 父进程确认 guardian pid 不存在 | 不能推出上下文从未打开，也不能推出平台动作没发生 |
| 上下文曾打开 | `context_opened: boolean` | 父进程**确实收到** `context-opened` | 不能推出上下文已关闭 |
| 提交状态 | `submission_state: 'NOT_SUBMITTED' \| 'UNKNOWN'` | 是否可能已经取得提交权限 | `UNKNOWN` 不等于"已提交"，`NOT_SUBMITTED` 也不等于"平台没被触及" |

**no-progress 记录里根本没有 `context_closed` 字段**（schema 层面不可伪造）。它也无法被当作关闭证明读回：`readClosure` 对 no-progress 记录抛 `GUARDIAN_UNCONFIRMED`。

四个 protocol version 的分工：

| protocol_version | 谁写 | 关键字段 | 允许把 environment 投影为 CLOSED |
| --- | --- | --- | --- |
| `kff.guardian-closure.v1` | child | `context_closed: true` | ✅（`recordQuiescence` 只在 v1 下置 `browser_status='CLOSED'`） |
| `kff.guardian-closure-compact.v1` | 保留策略压缩 | 由 v1 压缩而来，`context_closed: true` | ✅（`closureProof` 归一为 v1） |
| `kff.guardian-closure-startup-failed.v1` | 父进程 | `context_opened: false` | ❌ |
| `kff.guardian-closure-no-progress.v1` | 父进程 | `phase` / `process_terminated` / `context_opened` / `submission_state` / `forced` / `waited_ms` / `grace_ms` | ❌ |

`quiescenceInput.protocol_version` 是这三个（v1 / startup-failed / no-progress）的 enum：两种新证明都能释放 command，但只有 v1 能宣称浏览器已关闭。

## 5. 终止与进程树（Windows 实测）

`apps/agent/src/process-tree.ts`（本项目最小必要实现，未引入 supervisor 框架）：

```ts
terminateProcessTree(pid): win32 → taskkill /PID <pid> /T /F
                           posix → kill(-pid, SIGKILL)，失败再 kill(pid, SIGKILL)
isProcessAlive(pid)      : kill(pid, 0) 探针
```

实测（`tests/unit/process-tree.test.ts`，真实两级进程树，不用文档推断）：

- 只 `child.kill()`：直接子进程消失，**孙进程仍然存活** → 单独 kill 不足以终止浏览器。
- `terminateProcessTree()`：父子两级都消失。
- `isProcessAlive`：对已回收 pid、从未存在的 pid 都返回 false 而不抛错。

## 6. 从终止到收口的完整状态迁移（DB 层）

```
guardian 无进展
  → watchdog：不再发 submit-granted        （actions.state 保持 PREPARING）
  → stop → 强制终止 → process_terminated=true
  → 写 no-progress 记录
  → runGuardian reject GUARDIAN_NO_PROGRESS
  → main.ts finally → flushActionJournal
       ├─ readClosureEvidence 存在（否则整轮 gate 保持关闭，不 flush）
       ├─ commands/<id>/status  → action_state
       ├─ 构造 report（action_state ∈ {SUBMITTING,SUBMITTED} 时 NEEDS_HUMAN→UNKNOWN_OUTCOME）
       ├─ action-reports        → acceptReport
       └─ commands/<id>/quiescence → recordQuiescence
```

`acceptReport` 在收到本轮报告后的迁移：

| 目标 | 结果 |
| --- | --- |
| `action_attempts` | `state = report.outcome`，`completed_at = now()`（**不新增** attempt） |
| `agent_commands` | `state = 'DONE'` |
| `resource_leases` | `GUARDIAN_NO_PROGRESS` / `UNKNOWN_OUTCOME` / `AGENT_RESTART` ⇒ `quarantined = true`，`holder_attempt_id` 保留；其他 ⇒ `quarantined = false`，`holder_attempt_id = NULL`，`expires_at = clock_timestamp()` |
| `environments` | 隔离时 `state = 'QUARANTINED'`，否则 `'IDLE'`；`browser_status` 只有在 v1 证明下才可能变 `CLOSED` |
| `runs` / `tasks` | `UNKNOWN_OUTCOME` / `NEEDS_HUMAN` ⇒ `NEEDS_HUMAN`；`CANCELED` ⇒ `CANCELED`；`VERIFIED_SUCCEEDED` ⇒ `SUCCEEDED` |

`recordQuiescence` 的前置条件不变（B01 保留）：command 必须 `DONE/EXPIRED`、证明的 `command_id` / `action_id` 必须与行一致、同摘要重复调用幂等（`guardian.quiesced` 审计事件只有一条）。

## 7. 零重放与恢复

- **旧 action 不自动重发**：恢复路径只写事实（report + quiescence），从不 INSERT 新 attempt、从不重发平台动作。终态断言：`action_attempts` 1 行、`action.reported` 审计 1 条、`agent_commands` 1 行。
- **Command 1 永不重执行**：其 command 已 `DONE`，属于终态；journal 中该条目标记为 `quiesced`，后续 flush 直接跳过。
- **隔离语义保持**：结果不确定时 environment 保持 `QUARANTINED`、lease 保持 `quarantined=true`、run/task 保持 `NEEDS_HUMAN`，等待人工复核（`releaseQuarantine` 是人工路径，本轮不触碰）。
- **execution slot**：`agent_single_execution_slot` 随命令终态释放，第二合法命令可被真实 claim 并真实执行（见 `B01.1-test-results.md` §3）。

## 8. 本轮没有建立的机制（避免误读）

- 没有第二套 Guardian 状态机：阶段、settle、startup-failure、journal flush、quiescence gating 全部沿用 B01 的实现路径，本轮只在同一条路径上补了阶段预算与终止阶梯。
- 没有"总计时器"式看门狗：不存在一个与阶段无关的全局 deadline。
- 没有把超时写成 CANCELED / VERIFIED_FAILED：映射表见 §3，CANCELED 仅限 `awaiting-ready` 且从未 `ready`。
- 没有"进程死了 ⇒ 上下文没开 / 平台没动作"的推断：见 §4。
