# B01.2 保证模型：四个互不推导的事实

本轮的核心不是"多写几个测试"，而是把 B01 / B01.1 里被压缩成一个布尔量的四件事**在类型、证据、数据库门槛三层上彻底拆开**，并让每一层都能单独被证伪。

---

## 1. 被拆开的四件事

| # | 事实 | 含义 | 判定者（production path） | 载体 |
| --- | --- | --- | --- | --- |
| F1 | **Command lifecycle** | 这条命令在控制面走到哪一步 | `packages/core/src/execution.ts`：`acceptReport` / `recoverExpired` | `kff.agent_commands.state` ∈ `QUEUED / CLAIMED / DONE / EXPIRED` |
| F2 | **Guardian execution quiescence** | 执行槽位（execution slot）能不能被下一条命令复用 | `packages/core/src/reconciliation.ts`：`recordQuiescence` | `kff.agent_commands.quiesced_at` + `guardian.quiesced` 审计事件里的 `proof` |
| F3 | **Process tree termination** | Guardian 那棵进程树是否**被证明**已经不存在 | `apps/agent/src/process-tree.ts`：`probeProcess` + `listDescendants` + `composeTreeState` / `treeStateFrom` | 证据文件 `termination.process_tree` ∈ `ALIVE / DEAD / UNKNOWN` |
| F4 | **Browser-environment closure** | 那个浏览器环境能不能交给下一条命令 | `reconciliation.ts`：`releaseQuarantine`（普通放行）；`acceptReport` 的 `quarantine` 判定（保持隔离） | `kff.environments.state` / `browser_status`，`kff.resource_leases.quarantined` |

**F1 是账本，F3 是物理事实。** 这是本轮最重要的一句话：`DONE` / `EXPIRED` 只说明控制面把这条命令记完了，它对"那个进程还在不在"一无所知。

## 2. 四条不可推导关系（规划端 §四）

| 关系 | 现在成立的原因（代码位置） |
| --- | --- |
| `EXPIRED` ⊬ `guardian_quiesced=true` | `recoverExpired`（`execution.ts:256`）：`quiesced_at` **只在 `neverClaimed` 分支**写 `now()`，claimed 分支原样保留 NULL。claimed 命令即使过期，`quiesced_at` 仍是 NULL，`releaseQuarantine` 的第一个 pending 查询（`reconciliation.ts:97`）就会拦住。 |
| `guardian_quiesced=true` ⊬ `browser_closed=true` | `releaseQuarantine`（`reconciliation.ts:107-116`）：`quiesced_at IS NOT NULL` 只让命令进入候选，真正放行还要求它的 `guardian.quiesced` 证明**有且只有一条**，且 `protocol_version` ∈ {`kff.guardian-closure.v1`, `kff.guardian-closure-startup-failed.v1`}。终止记录（`…-no-progress.v1`）即使 tree 是 `DEAD` 也进不了这一关。 |
| `root_pid_dead=true` ⊬ `process_tree_dead=true` | `treeStateFrom`（`process-tree.ts:134`）：`enumeration === 'UNAVAILABLE'` ⇒ `UNKNOWN`，与 root 探测结果无关；`composeTreeState`（`:122`）只要有 `ALIVE` 就是 `ALIVE`、否则只要有 `UNKNOWN` 就是 `UNKNOWN`，部分答案永不向上取整为 `DEAD`。单测 `reports ALIVE when the root is gone but a descendant it started is still running` / `refuses to infer a dead tree from a dead root when no listing was obtained` 用真实进程钉住这两条。 |
| `no-progress` ⊬ `environment releasable` | `recordQuiescence`（`reconciliation.ts:16`）：no-progress 证明在 `process_tree !== 'DEAD'` 时直接 `GUARDIAN_UNCONFIRMED`(409)；`acceptReport`（`execution.ts:212,217`）：`guardian.process_tree !== 'DEAD'` ⇒ 命令**不写 `DONE`** 且强制 quarantine；`releaseQuarantine` 的证明版本门槛再拦一次。三层都拦。 |

## 3. 三态终止语义（规划端 §三 的落地）

`ProcessState = 'ALIVE' | 'DEAD' | 'UNKNOWN'`（`process-tree.ts:14`），全链路只有这一套取值，runtime 与 Zod schema 共用 `guardianTimingLimits` / `processTreeState`（`packages/contracts/src/index.ts`）。

| 树状态 | 允许 | 禁止 |
| --- | --- | --- |
| `DEAD` | 可以继续判断是否形成 Guardian execution quiescence（`recordQuiescence` 接受 no-progress 证明；`acceptReport` 允许命令写 `DONE`） | 仍然**不能**据此放行 environment（F2 ⊬ F4） |
| `ALIVE` | 记录事实、写 `NEEDS_HUMAN`、保持隔离 | 禁止形成可释放 execution slot 的 quiescence proof；environment 必须继续 `QUARANTINED` |
| `UNKNOWN` | 与 `ALIVE` **完全同等严格**（fail-closed） | 同上，且禁止把它当作"没有证据"降级处理 |

判定的来源只有两个，且都不允许"猜"：
- `probeProcess(pid)` —— `process.kill(pid, 0)`；`ESRCH` ⇒ `DEAD`，其余任何错误（含 POSIX 的 `EPERM`）⇒ `UNKNOWN`。`catch => false`（"探测失败就是死了"）在本轮被彻底删除。
- `listDescendants` —— 终止前枚举（`taskkill /T` 之后父链就没了）；枚举不可得 ⇒ 整棵树 `UNKNOWN`。

`terminateProcessTree()` 返回的 `GuardianTermination` 把四种独立信息分列，互不代言：

```
{ process_tree: ALIVE|DEAD|UNKNOWN,   // 判决（由 root + descendants 组合）
  tool: SUCCESS|FAILED|TIMEOUT|ERROR|SKIPPED,  // 工具自身干了什么
  root: ALIVE|DEAD|UNKNOWN,           // 根进程
  descendants: ALIVE|DEAD|UNKNOWN,    // 枚举到的后代
  sampled: number,                    // 枚举到几个后代
  enumeration: LISTED|UNAVAILABLE,    // 有没有拿到进程表
  elapsed_ms: number }
```

"工具成功"≠"根死了"≠"树死了"：`tool: FAILED + root: DEAD + process_tree: ALIVE` 是单测里的一个真实组合（Windows 上对已消失的 pid 调 `taskkill` 退出码 128）。

## 4. Weak → Strong 证据升级规则

同一份 proof 文件（`<runtime>/agent/closures/<command_id>.json`）有两个写者：父进程（被迫终止，写 weak）和子进程（自己关掉了上下文，写 strong）。它们是不同进程，可能同时活着。规则写在 `apps/agent/src/guardian-protocol.ts`：

| 概念 | 取值 |
| --- | --- |
| 证据强度 `closureStrength` | `PROVEN_CLOSED`(3) > `NEVER_OPENED`(2) > `PROCESS_ONLY`(1) |
| 临时文件后缀 | `closure` → `.closure.tmp`，`startup` → `.startup-failed.tmp`，`noProgress` → `.no-progress.tmp`，`compact` → `.compact.tmp`（**按 kind 分开**，weak writer 不会删掉 strong writer 的 .tmp） |

写入规则（`saveEvidence`）：
1. 独占创建：先 `linkSync(tmp, final)`（EEXIST 即"已存在"），失败回退 `renameSync`；最多重试 4 次。
2. **强替换弱**：新证据强度 > 磁盘上的 ⇒ 覆盖。
3. **强不被弱覆盖**：新证据强度 < 磁盘上的 ⇒ 拒绝。
4. **同强度同实质**（`substance()` 忽略 `closed_at`）⇒ 幂等，返回磁盘上那份（重放同一个记录不会得到两份）。
5. **同强度不同实质** ⇒ `IDEMPOTENCY_CONFLICT`。
6. 解析不了的既有文件 ≠ 不存在（`parseEvidenceFile`），不会被弱证据当成空位覆盖。

已记录但**未**解决的边界：weak writer 与 strong writer 在"同一毫秒"竞争时，最终胜者是文件系统独占创建的结果，而不是仲裁结果——两条路径都不会写出一个错误的事实（弱证据不会被读成关闭证明），但**谁赢不可预测**。见 follow-up ledger。

## 5. 数据库侧的三道门槛（顺序即语义）

`acceptReport` → `recordQuiescence` → `releaseQuarantine`，三道门依次收紧：

1. **命令能不能算完成**（F1）：`report.guardian` 存在且 `process_tree !== 'DEAD'` ⇒ 不写 `DONE`，`audit action.reported` 记 `command_completed:false`、`guardian_tree:'UNKNOWN'`。
2. **槽位能不能复用**（F2）：`recordQuiescence` 只接受 `state ∈ {DONE, EXPIRED}` 且 （`closure.v1` / `startup-failed.v1` / `no-progress.v1 且 process_tree === 'DEAD'`）。
3. **环境能不能交还**（F4）：`releaseQuarantine` 要求 action 已终局、无提交意图、无 pending 命令、且每条已 quiesce 的命令都有一条**唯一**的、版本为 `closure.v1` 或 `startup-failed.v1` 的证明。**终止记录永远不放行 environment。**

第 3 道的操作后果（诚实披露）：一条只拿到"树已死"证明的命令，其 environment 今天**没有**任何自动放行路径——它会一直保持 `QUARANTINED`，直到未来有一个显式的人工 override 设计。这是本轮 fail-closed 的**有意结果**（规划端 §一 P1-02「禁止借现有普通 release 路径偷偷放行 override」），但它确实是一个运营缺口，已进 ledger。

## 6. Retention 不得覆盖安全事实（P1-03）

`apps/agent/src/action-journal.ts`：
- `retainedSafety(record)` 从 **closure 记录**（而不是 report）读取两件事：`termination`（进程事实）与 `GUARDIAN_NO_PROGRESS`（错误码）。
- `maintainActionJournal` 在**任何变更之前**读取记录，拒绝时整体不写；retention 合成 report 时 `...safety` 展开在最后，因此页面载荷与终局结论归 retention，安全事实归记录。
- `flushActionJournal` 在把 closure 转成 report 时携带 `guardian`（`result.guardian = termination`），让接收端能独立判断"能不能释放槽位"。

因此 `GUARDIAN_NO_PROGRESS + retention expiry` 的结果是：command 在 `recoverExpired` 后变成 `EXPIRED` 且 `quiesced_at IS NULL`，action 停在 `BLOCKED/GUARDIAN_NO_PROGRESS`，environment 保持 `QUARANTINED`——**不会**因为"页面过期"而自动变 IDLE。集成用例 `keeps a no-progress termination quarantined through retention expiry and recovery` 端到端钉住这条。

## 7. 本轮**没有**声称的东西

- POSIX（Linux / macOS）的进程组终止**未验证**：`runGroupKill` 在本机（Windows 11）不可达，单测里是 2 个 `it.skip`，不是 PASS。见 `B01.2-test-results.md` §6。
- "settle 之后到达的 `context-opened`"没有端到端用例（子进程只有在真实 `BrowserContext` 打开后才会发这条消息，而每条 settle 路径要么杀掉子进程、要么断开通道）。它由 `settle()` 里的 `child.off('message', onMessage)` + `onMessage` 顶部的 `if (settled) return;` **结构性**保证，被列为下一轮浏览器级验收项，**不写成 PASS**。
- Job Object / cgroup 级别的树终止**未**引入；本轮只保证"不制造虚假的 tree terminated 事实"。
