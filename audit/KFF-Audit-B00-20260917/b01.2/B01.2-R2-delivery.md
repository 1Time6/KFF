## 3. onSpawn 改动的完整 hunk、必要性与授权条款

### 3.1 完整 hunk

```diff
@@ apps/agent/src/guardian.ts @@
-    child.on('message', async message => {
+    // The handler is a named declaration so `settle` can detach it: once a terminal decision is taken,
+    // this function must not run again for this child, whatever is still in flight on the channel.
+    async function onMessage(message: unknown) {
+      if (settled) return;
       if (!message || typeof message !== 'object' || !('type' in message)) return;
       if (message.type === 'ready' && !started) {
         started = true;
         progress('awaiting-start');
+        // A throwing hook used to reject the promise directly and leave the watchdog and the channel
+        // running behind it. It goes through the same one-shot terminal path as everything else.
         try { hooks.onSpawn?.(child.pid!); send({ type: 'start', ... }); if (hooks.signal.aborted) stop(); }
-        catch (error) { child.disconnect(); reject(error); }
+        catch (error) { settle(() => reject(error)); }
       }
```

**改动实质只有一行**（`child.disconnect(); reject(error);` → `settle(() => reject(error));`），
其余为该行所属的**同批 P1-01 重构**（`child.on('message', ...)` → 具名 `onMessage` + `settled` 早退），后者是 P1-01 的正式范围。
把整块一起给出，是因为单看那一行会看不到它已经处在 `onMessage` 之内。

### 3.2 必要性

P1-01 的硬要求是"**settle 之后所有 IPC 消息路径必须失效**"。`settle()` 正是摘监听 + 断通道 + 一次性终局的那道闸门。
BASE 的 `catch` 分支**直接 reject，不经过 `settle()`** ⇒ "已终局"与"通道已关"之间出现一个**不由 `settle()` 管辖**的缺口，
P1-01 的不变量在该路径上不成立。所以这一步不是顺手重构，而是 P1-01 在该路径上**成立的前提**。

### 3.3 授权条款

规划端 §二 把 P2-05 列为"记录即可，**除非** P1 的修复无法在不碰它的情况下保证统一终局不变量"。
本情形正落在该"除非"分支内，故按 §二 要求**先行报告**，并给出回退选项：
若规划端认为应保持 BASE 行为，可只回退这一行，代价是 `onSpawn` 抛错路径重新回到"不由统一 settle 管辖"的状态。

**对调用方的可见行为未变**：仍然是同一个 error 拒绝。**需规划端确认。**

## 4. §二 / §三 修复内容与预算分配

### 4.1 预算分配（§三 修复的主体）

**修复前**

| 调用方 `force` | `deadlineMs = floor(force/2)` | 枚举 `min(5000, deadline/2)` | kill `deadline − 枚举实际` |
|---|---|---|---|
| 5000（集成用例） | 2500 | **1250** | 1250 |
| 10000（生产默认） | 5000 | **2500** | 2500 |
| 24000（liveness 单测） | 12000 | 5000（触顶） | 7000 |

**修复后**

| 调用方 `force` | `settleReserve` | `deadlineMs` | 枚举上限 | kill 保底 |
|---|---|---|---|---|
| **5000（集成用例）** | 1000 | 4000 | **2667** | **1333** |
| 10000（生产默认） | 1000 | 9000 | **7500** | **1500** |
| 24000（liveness 单测） | 1000 | 23000 | **21500** | **1500** |

**总账恒等式**：`deadlineMs + settleReserve = force`，三档全部成立（4000+1000=5000，9000+1000=10000，23000+1000=24000）。
枚举拿到的是**上限**而非定额，没用完的时间自动回流给 kill；`MIN_ENUM_MS` / `MIN_KILL_RETRY_MS` 只决定"要不要再开一次尝试"，
不决定"能跑多久"，因此**不存在抬高子阶段下界导致总预算失效**的路径。

### 4.2 为什么这样切（实测依据）

| 负载 | 进程枚举（修复后实现） | taskkill `/T /F`（12 个 detached 后代） |
|---|---|---|
| 0.0× | 630 ms | 305 ms |
| 1.0× | 981 ms | 460 ms |
| 2.0× | 2166 ms | 966 ms（**最大 1143**） |

枚举占约 90% 成本且是**唯一在负载下崩塌**的一环；kill 是小而几乎不随负载变化的尾巴。
**原来的对半切分恰好切反**：饿死了真正需要时间的一环，把一半预算留给了从不用满的另一环。
`KILL_RESERVE_MAX_MS = 1500` 由 kill 的实测上界（2.0× 下 1143ms）确定。

> **注意**：这张表的 kill 成本（max 1143ms @2.0×）与集成用例 `force: 5000` 下的 kill 保底 **1333ms** 只差 17% 余量 ——
> 这正是 §7 中 3.0× 失败的直接来源。

### 4.4 §四.1 恢复链 1 的结论

## 5. NEW-B012-02 确定性测试证据

| 清理失败**不覆盖原判定** | 成立 | `removeTemp` 的裸 `catch` 吞掉一切；可观测形式是"报错来自 write 而非 unlink"，两个错误码在测试内**现场标定**、不硬编码平台码，并断言二者确实不同 |
| **不跳过必要重试** | 成立 | 未发布记录时不存在可重试对象；已发布时弱写者在**强度比较**处即被拒，根本到不了写路径 |
| **不丢失真实 closure** | 成立 | 已发布 closure 在 3 种 tmp 全被阻塞、3 个弱写者全部尝试后仍**逐字节不变** |

**`finally` 抛出这一支不可达 —— 按代码路径论证，非重复运行**：
`writeEvidenceFile` 的清理与写入用**同一个 tmp 路径**，任何让 unlink 失败的状态同时让 write 失败，
控制流根本到不了 `finally`。故该分支只能读代码证明：`removeTemp` 全捕获，且它是全模块**唯一的清理点**。

**遗留发现（记录，不自行放宽）**：陈旧 tmp 若为不可删除的目录，`saveEvidence` 的 4 次重试循环被**绕过**，
调用者收到**裸 fs 错误**（本平台 EISDIR）而非域错误码。
安全性未受损（fail-closed、无半成品记录、已发布证明不变），但**错误形态与模块其余部分不一致**。
这是**报告问题而非安全问题**，处置权在规划端。

## 7. **未解决**：负载支持范围的上限（3.0×）

**这是本轮最重要的未决项，必须由规划端裁定。**

单测文件独立跑（`browser-message.test.ts` 单条用例）的实测：

| 负载 | 用例耗时 | 结果 | 失败点 |
|---|---|---|---|
| 0.0× | 8.8 s | **pass** | — |
| 1.0×（全文件内） | 17.3 s | pass | — |
| 1.5× | 19.1 s | pass | — |
| 1.5× | 28.4 s | **fail** | `:203`（见 §8） |
| 2.0× | 29.0 s | pass | — |
| 2.0× | 34.7 s | **fail** | `:203`（见 §8） |
| 2.0×（全文件内） | 38.7 s | **fail** | `:203`（见 §8） |
| **3.0×** | 48.6 s | **fail** | **`:180` —— 守护进程被活着遗弃** |

**3.0× 的失败是本次修复的能力边界，不是 §8 的租约问题**：`:180` 是 `isProcessAlive(guardian)` 10 秒轮询，
失败即"进程树终止失败、守护进程仍然活着"。这正是裁定 §一 要求修复的**第二饥饿模式**，它在 3.0× 下**依然存在**。

**算术依据**（集成用例传 `force: 5000`，是**测试预算**）：

- `settleReserve` = min(floor(5000/5), 1000) = **1000**
- `deadlineMs` = 5000 − 1000 = **4000**
- `killReserve` = min(floor(4000/3), 1500) = **1333**
- `enumDeadline` = 4000 − 1333 = **2667**

而 §4.2 实测 taskkill 在 2.0× 已达 **max 1143ms**，与 1333ms 保底只差 **17%**。
负载再升一档，kill 必然吃满整个时间片 → `TIMEOUT` → 重试因 `slice < MIN_KILL_RETRY_MS` 不再开 →
**守护进程存活**。这与观测到的 `:180` 失败一致。

**未测量、不得当成已知的部分**：我没有在 3.0× 下单独测枚举耗时，
因此**不能断定**是"枚举先吃满 2667ms"还是"kill 拿 1333ms 不够"先触顶 —— 两者都可能，甚至同时发生。
`enumDeadline` 只是**上限**，枚举用不完的时间会回流给 kill，所以两个份额是耦合的。

**另一种无法排除的解释**：`:180` 判的是 `isProcessAlive(pid)`。用例在 `:180` 就失败了，
**没有走到 `:185`**，所以那次的 `termination` 记录（`tool` 是 `TIMEOUT` 还是 `SUCCESS`）**没有被捕获**。
因此我**不能排除**"守护进程其实已死、只是 PID 被复用导致 `isProcessAlive` 报 true"这一可能
（3.0× 下有 24 个 node 自旋进程，PID 复用并非不可能）。
按代价排序我仍认为 kill 饥饿是主因（有上面的预算算术支撑），但**这是推论，不是观测**。
下一轮若要定案，应在该用例失败时一并落盘 `termination` 记录。

**生产配置（`force: 10000`）不同**：枚举上限 7500ms、kill 保底 1500ms，余量远大于集成用例。
但**我没有在 3.0× 下按生产配置实测过**，因此不宣称生产在 3.0× 可用 —— 那是**未验证**，不是通过。

### 7.1 决策选项（供规划端裁定，执行端不自选）

先给一个**会改变选择的算术事实**。当前
`killReserve = max(1, min(floor(budget / 3), KILL_RESERVE_MAX_MS))`，其中 `budget = deadlineMs = force − settleReserve`：

| force | budget | `floor(budget/3)` | 上限 `KILL_RESERVE_MAX_MS` | **实际 kill 保底** | 谁在约束 |
|---|---|---|---|---|---|
| 5000（集成用例） | 4000 | **1333** | 1500 | **1333** | **`budget/3`，不是上限** |
| 10000（生产） | 9000 | 3000 | **1500** | **1500** | 上限 |

**⇒ "提高 `KILL_RESERVE_MAX_MS`"对失败中的集成用例是空操作**：只要新上限 ≥ 1333，
`force=5000` 下保底恒为 1333，改多少都一样。该杠杆**只对 force 大的生产档有效**。

（上表与 §7.1 各选项数值均由脚本按当前公式实算复核，非手推：`max=1500/2000/3000` 三档在 `force=5000` 下
输出**完全相同**；选项 C 在 `force=10000` 下输出与现状**完全相同**。）

| # | 选项 | 具体改动 | force=5000（失败档） | force=10000（生产） | 前置测量 | **不解决** |
|---|---|---|---|---|---|---|
| **A** | 只补测量，本轮不动生产代码 | 无 | 无 | 无 | 3.0× 下 kill 成本、枚举成本各测一遍；**并在失败时落盘 `termination` 记录** | 不修复；但消除 §7 两个"未测量"与 PID 复用歧义 |
| **B** | 提高 `KILL_RESERVE_MAX_MS` | 1500 → 更大 | **无效果**（见上表） | kill 保底 1500 → 更大，枚举上限相应缩小 | 需 3.0× kill 上界以定新值 | 集成用例；且缩小生产枚举上限，可能把 DEAD 变成 UNKNOWN |
| **C** | kill 份额分数 1/3 → 1/2 | `min(floor(budget/2), MAX)` | kill 保底 **1333 → 1500**，枚举上限 2667 → **2500** | **无变化**（仍 1500/7500，上限约束） | 无（已测：L 在 2.0× 为 2166/最大 2233，4/4 ≤ 2500） | 3.0× 仍失败，但**失败形态改变**：枚举超 2500 ⇒ `UNAVAILABLE` ⇒ **UNKNOWN（fail-closed）**，而不再是被活着的守护进程（见下） |
| **D** | 按**生产配置**补测 3.0× | 无（只测） | 不适用 | 判定生产在 3.0× 是否真的有问题 | 一次 force=10000 的 3.0× 运行 | 不修复；但 §7 现有结论全部基于 force=5000，**生产 deadline 是它的 2.25 倍** |
| **E** | 接受 2.0× 为支持上限 | 文档 | 不适用 | 不适用 | 无 | 把 3.0× 记为已知边界。**注意裁定 §一 明确"不得仅凭负载问题降级"**，选此项需独立的容量论证，而非"负载高"一句话 |
| **F** | 改集成用例的 `force` 5000 → 10000 | 改测试 | kill 保底 1333 → 1500，deadline 4000 → 9000 | 不适用 | 无 | **这是改被测配置，不是修生产**；且会让测试变宽，需显式授权，否则触碰"不得放宽" |

**关于 C 的形态变化值得单独说明**：当前 3.0× 的失败点是 `:180`「守护进程仍活着」——
即裁定 §一 要求修掉的**第二饥饿模式仍然存在**。若把 kill 份额提到 1/2，3.0× 下更可能先在枚举处超时，
得到 **`UNKNOWN`**：仍然是红测，但结论从"树可能还活着"变成"**无法证明树已死**"，后者才是设计语义，
且必定 fail-closed。**两项都失败，区别在失败是否诚实** —— 执行端不替规划端判断哪个可接受。

**保守停止在所有选项下都成立**：3.0× 的失败是 fail-closed（环境留在 `QUARANTINED`/`RUNNING`，不释放槽位）。

## 8. 2.0× 下的那条红测：`flushActionJournal` 返回 false

**这不是枚举/终止的失败。** 同一次运行里 `:194` 的 `termination` 断言**通过了**
（`process_tree:'DEAD'`、`enumeration:'LISTED'`）—— 即 §二/§三 的修复在 2.0× 下生效。
失败发生在其后的 `:203`：`expect(await flushActionJournal(...)).toBe(true)` 收到 `false`。

### 8.1 已证实的事实

用单条用例 + 保留失败库（`KFF_TEST_DATABASE`）取得，**失败现场的真实 DB 状态**（1.5× 与 2.0× 两次一致）：

- `kff.agent_commands`：`state='CLAIMED'`，`quiesced_at IS NULL`（命令**未**收口，槽位未释放）
- `kff.actions`：`state='SUBMITTING'`（回执**未**被接受）
- `kff.resource_leases`：两条租约 `held=true`、`quarantined=false`，**检查时已过期**
- `kff.audit_events`：**没有** `guardian.quiesced` 事件（关闭证明从未写入）
- `kff.environments`：`state='BUSY'`、`browser_status='RUNNING'`（环境**仍被隔离**，未被误放行）

**全程 fail-closed，无安全后果。**

`flushActionJournal` 返回 `false` 的三条路径中，`:68`（无 closure）可排除（`:185` 刚成功读到记录）；
可疑的是 `:96` 捕获 `LEASE_STALE`/`VERSION_CONFLICT` 后置 `quarantined` 再于 `:100` 返回 false。
其上游 `acceptReport`（`execution.ts:180`）会调 `validateLeases`（`:33-40`），
而资源租约由 `execution.ts:100` 以 **30 秒** TTL 发放，由 **`agentHeartbeat`（`execution.ts:114`，续租在 `:126`）** 续租 ——
**集成用例不跑 heartbeat**。

### 8.2 **未证实**的部分（不得当成结论）

我最初的假设是"claim→flush 超过 30 秒 TTL"。**这个假设的朴素形式已被自己证伪**：
在 1.5× 那次失败（耗时 28.4s）中，我把 `validateLeases` 的三个条件**逐条按 claim+28.1s 这个时刻**在保留库里求值，
**三条全部成立**（命令 `CLAIMED` 且 `expires_at` 未到；`action_attempts.leases` 恰好 2 条且 token 匹配；
两条资源租约在库中存活、持有者正确、未被 quarantine）。所以**不能用"30 秒到期"解释那一次**。

之后我做了**临时插桩**（在 `flushActionJournal` 的三个 `return false` 点与 `catch` 处打点），
跑 1.5× / 2.0× / 3.0× 各一次：

- 1.5× **通过**（19.1s），2.0× **通过**（29.0s）—— 这两次没触发
- 3.0× 失败在 **`:180`**（§7 的问题），**根本没走到 flush**，未产生任何插桩输出

即：**该失败是间歇性的，且插桩本身扰动时序，我没能在插桩下抓到它。**
插桩已**完全回退**，`action-journal.ts` sha256 与插桩前一致，快照与工作树逐字节相同（见文首）。

**因此，`false` 的确切来源（`:77` 的 status 分支 / `:91` 的 redaction 分支 / `:96` 的租约分支）本轮未确定。**
它**是负载相关的**（0×/1.0×/1.5×-快 通过；1.5×-慢、2.0×、2.0×-全文件 失败），
且与**用例自身耗时**相关，但**边界不等于 30 秒**，机制**未证实**。

### 8.3 是否可以归因于本轮修复

**没有同条件对照（BASE 跑 2.0×）**，因此按裁定"没有同条件对照证据，不再将'不是回归'写成确定结论"，
我**不写"不是回归"**。本轮进一步查明：该对照**在结构上不可得**（死结论证见 **§8.4.1**，非本节推论）。能说明的只有：

- 失败点在 `flushActionJournal`，其调用链（`acceptReport` → `validateLeases` → 资源租约）**不经过**
  本轮改动的 `process-tree.ts` / `guardian.ts` / 预算常量；本轮改动只影响 `termination` 字段的**内容与耗时**。
- 本轮修复让 `:194` 在 2.0× 下**首次通过**（修复前该处会因 `enumeration='UNAVAILABLE'` 先失败），
  因此**这个下游失败是被本轮修复"解锁"后才暴露出来的**，不是被引入的 —— 但这仍是**推论，不是对照证据**。

### 8.4 决策选项（供规划端裁定，执行端不自选）

**先纠正一处口径**：本轮核查发现 `apps/agent/src/process-tree.ts` **在审计 BASE（`752042bc`）上并不存在** ——
BASE 的终止逻辑是一个**同步、无超时、返回 boolean** 的 `terminateProcessTree`（`spawnSync('taskkill', …, '/T','/F')`）。
三态、枚举、deadline 全部是**本批新增**（HEAD `c293aa7` 处该文件为 20 行的原实现，工作树扩到 262 行）。
因此 §8.3 里"BASE 对照"的含义必须分清：**BASE 与本轮改动不是同一实现的两次运行**。

#### 8.4.1 同条件对照为何不可得（这一条本身是结论）

要用对照判定"是否回归"，需要某个**修复前状态在 2.0× 下走到 `:203`**。三条路都走不通：

| 候选对照 | 在 2.0× 下会怎样 | 证据 |
|---|---|---|
| **BASE `752042bc`** | `browser-message.test.ts` 里**根本没有** `flushActionJournal` / `process_tree` 断言块 —— 该断言是本批新增，无对照可言 | `git show 752042bc:tests/integration/browser-message.test.ts \| grep` 无输出 |
| **R1（R2 前的工作树）@ 负载** | 死在**更早**的 `expect(await isProcessAlive(guardian)).toBe(false)`：`AssertionError: expected true to be false` | `b01.2-repro-loaded.log:147,169`（5 failed / 7 passed） |
| **R1 空载（全量集成）** | 死在 `termination` 断言（旧行号 `:186`/`:272`）：`enumeration='UNAVAILABLE'` | `b01.2-full-integration-fail.log:568,590,601,623` |

**⇒ 这是一个死结**：R1 只有在负载足够低、能通过 `termination` 断言时才可能走到 `:203`，
而低负载恰恰是 `false` **不出现**的区间。**"是否回归"在本测试上不是"尚未测量"，而是"结构性不可判定"。**
（另记一处证据缺口：`b01.2-repro-loaded.log` **没有记录 spinner 数**，其确切负载未知 —— 它用的不是
`b012-fix-load.sh` 那套带表头的harness。下一轮若复用该结论，需补记负载。）

#### 8.4.2 定位 `false` 来源的选项

| # | 选项 | 做什么 | 能否定位到具体路径 | 对时序的扰动 | 生产代码改动 |
|---|---|---|---|---|---|
| **G** | **非侵入式记录** | 用例里包一层 controller：每次调用连同抛出的 `AppError.code` 记进数组，失败时 dump | **能**（`:96` 会留下 `LEASE_STALE`/`VERSION_CONFLICT`；`:77`/`:91` 无异常但可由调用序列区分） | **极小**（只多一次数组 push） | 无 |
| **H** | 控制端故障注入 | 让 controller 可按指令抛 `LEASE_STALE` / 返回非 `READY` / 触发 mid-flush redaction | **能**，且**确定性** | 无（不再依赖负载） | 无（改测试） |
| **I** | 测试内 heartbeat 循环 | 按生产节奏调 `agentHeartbeat` 续租 | 只能证实/证伪"租约到期"假说 | **中等**（定时器本身影响调度） | 无 |
| **J** | 新增 flush 确定性单测 | 假 controller 分别强制三条路径 | **不能**解释集成里的那次；但能证明三条路径各自 fail-closed | 无 | 无 |
| **K** | 租约 TTL / 放宽测试 | 提高 30s TTL 或让用例跳过租约校验 | 不定位 | 无 | **有**（TTL 是陈旧度上界，触碰裁定 §二"不得降低安全门槛"，需强论证） |

**G 与 H 是互补的**：G 抓**真实发生的那一次**（不改控制流），H 把三条路径**逐个钉死**。
只做 J 会得到一个"代码是对的、但集成里为什么返回 false 仍不知道"的结论。
I 只有在 G 或 H 已经指出嫌疑路径之后才有判别价值。

#### 8.4.3 与 §7 的耦合（排期需注意）

§8 的复现依赖"用例至少跑到 `:203`"。而 §7 表明 **3.0× 下用例连 `:180` 都过不去**，
所以 §8 的可复现负载窗口是 **1.5×–2.0×**，比 §7 更窄。
**若先按 §7 选项 C 调整 kill 份额，`:180`/`:194` 的通过区间会改变，§8 的复现窗口需重新标定。**

- 三态判定、枚举失败 ⇒ `UNKNOWN`、组合规则、PID 身份（`dup_pids=0`）
- 预算切分与总账恒等式（§4.1）
- 枚举实现替换后的**父子关系 / 覆盖完整性 / 失败分类 / PID 身份**四项
- taskkill 路径、退出码语义（gone pid ⇒ 128 ⇒ `FAILED`）
- NEW-B012-02 的四个边界故障用例
- 负载支持范围**到 2.0×**（§7）；3.0× **不成立**

**POSIX —— `UNVERIFIED`，本轮未验证，不得读作 PASS**：

- `runGroupKill`（`process-tree.ts`）在本机**从未被执行**（`process.platform !== 'win32'` 分支）
- `runGuardian` 在 POSIX **未**建立进程组，`kill(-pid)` 可能失败并留下后代（= LEDGER-P2-02）
- 两条 POSIX 用例保持 `it.skip`，是**跳过**而不是通过 —— **没有任何测试结果可以读作证明**
- 本批次**不宣称** Linux / macOS 的生产进程树终止已验证
