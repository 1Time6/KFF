# B01.2 总结（Guardian safety closure）

本轮只做 **Guardian 安全收口**：不扩功能，不动 Reception / Acquisition / Inbox 业务规则，不重构无关模块，不 commit / merge / push。

## 0. 一句话结论

B01.2 的六项（P1-01 / P1-02 / P1-03 / P1-04 / P2-01 / P2-03）**全部落地**；单元 / 契约 / 类型 / 静态检查 / 单文件集成全绿，**全量集成 418/420**——2 条失败不是回归，而是本批 fail-closed 语义的运营代价被实测出来（负载下进程枚举超时 ⇒ 树降级 `UNKNOWN`，详见 §5 与 §6.2 LEDGER-NEW-08，**请在复审时先看这一条**）。核心变化是：**"命令结束"、"执行槽位可以复用"、"进程树被证明已终止"、"浏览器环境被证明已关闭"这四件事，在类型、证据文件、数据库门槛三层上不再互相推导**。`process_terminated: boolean`（一个可以被 root-only 探测置真的布尔量）被删除，换成三态 `termination.process_tree ∈ {ALIVE, DEAD, UNKNOWN}`；只有**被证明的 `DEAD`** 才允许形成可释放执行槽位的 quiescence proof，而**任何**终止证明都不再能通过普通 release 路径交还浏览器环境。`ALIVE` 与 `UNKNOWN` 一律 fail-closed：命令不写 `DONE`、`recordQuiescence` 拒绝、environment 保持 `QUARANTINED`。

### P1-02（command lifecycle / Guardian quiescence / browser closure 三者拆开）

- **类型层**：`quiescenceInput` 的三个变体各自携带**自己的**事实（closure.v1 = 上下文已关闭；startup-failed.v1 = 从未打开；no-progress.v1 = 进程终止 + 必填 `process_tree`）。
- **写入层**：`recordQuiescence` 只认 `state ∈ {DONE, EXPIRED}`，且 no-progress 必须是 `DEAD`。
- **释放层**：`releaseQuarantine:107-116` 逐个命令要求**唯一**一条 `guardian.quiesced` 证明，且版本 ∈ {`closure.v1`, `startup-failed.v1`}；因此 `state=DONE/EXPIRED + quiesced_at` **不足以**恢复 IDLE——这正是规划端要求的那一条。
- **不允许偷偷放行 override**：普通 release 路径里没有"跳过证明"的分支；`recoverExpired` 的 claimed 分支不写 `quiesced_at`。
- 集成证据：`refuses to release an environment on a termination proof even when the tree was proven dead`（对照组用**真实 closure** 放行另一个环境 ⇒ 门槛不是"一律拒绝"）；`completes a command on a proven-dead tree and still refuses to release its environment`（`DONE` + 审计 `command_completed:true` 也不放行）。

### P1-03（retention 不得覆盖 Guardian safety facts）

`action-journal.ts` 的 `retainedSafety()` + `maintainActionJournal` 的"先读记录、再决定是否整体拒绝"。集成证据：页面过期后由记录**合成**的回执仍带 `{outcome:'BLOCKED', error_code:'GUARDIAN_NO_PROGRESS', guardian_tree:'UNKNOWN', command_completed:false}`；命令随后 `EXPIRED` 但 `quiesced_at IS NULL`、environment 仍 `QUARANTINED`。

### P1-04（taskkill 纳入真 deadline）

- `runToolWithDeadline`：spawn + `setTimeout` → `SIGKILL` → `TIMEOUT`；`error` → `ERROR`；退出码 0 → `SUCCESS`，非 0 → `FAILED`（**不再**把 "工具退出" 当成 "进程已终止"）。
- `guardian.ts:238-240`：`forcedUntil = now + policy.force`，终止调用只拿到 `floor(policy.force/2)`，之后的等待只拿剩余时间。
- watchdog 的 bounded liveness **覆盖终止工具本身**：工具超时也被记进 `termination.tool`。
- 证据：`ends a tool that outlives its deadline instead of waiting for it`（真实 60s 睡眠的 node 在 400ms 内被 `TIMEOUT`）、`proves nothing about a tree it could not enumerate, and ends the tool at its deadline`（`taskkill` 在 1ms deadline 下 `TIMEOUT`）。

### P2-01（三态 + 不得用 `catch => false` 代表死亡）

- `classifyProbeFailure`：`ESRCH` → `DEAD`；**其余一切**（含 POSIX `EPERM`、无权限、未知错误）→ `UNKNOWN`。
- `isProcessAlive = probeProcess(pid) !== 'DEAD'`（UNKNOWN 与 ALIVE 同等严格）。
- root PID 消失**不**单独证明整棵树：`treeStateFrom`（枚举不可得 ⇒ `UNKNOWN`）与 `composeTreeState`（部分答案不向上取整）。
- 终止证明区分四件事：`tool` / `root` / `descendants` / `process_tree`（`sampled` + `enumeration` 记录枚举到什么程度）。
- `main.ts` 的 `process.lock` catch-all / EPERM 同类问题：**未改**，按规划端指示记入 ledger。

### P2-03（liveness 参数边界统一 + fail fast）

- 单一来源 `guardianTimingLimits = { min_ms: 100, max_ms: 86400000, max_total_ms: 86400000, test_min_ms: 1 }`，runtime policy 与 evidence schema 共用。
- `guardianLivenessPolicy` 对 `undefined` 以外的值：必须 `Number.isSafeInteger && >= min && <= max`，且**所有阶段之和** `<= max_total_ms`，否则 `AppError('GUARDIAN_LIVENESS_INVALID')`；**不再静默使用默认值**。
- `assertGuardianLivenessConfiguration()` 在 `main.ts` **取锁之前**调用；非法配置 ⇒ 非零退出、日志含错误码与变量名、**不留下 `process.lock`**。
- test override 的封印：`NODE_ENV === 'test'` **且** `runtime` 位于 `<KFF_ROOT>/.kff/agent-process-tests/`（路径比较，不是子串匹配）；两个条件缺一不可。

## 4. 最终语义（§八-11 .. §八-16）

| 条目 | 结论 |
| --- | --- |
| **ALIVE / DEAD / UNKNOWN 最终语义** | 三态贯穿 runtime、证据 schema 与数据库判定。`DEAD` 只能由"枚举成功 + root 与全部后代探测均为 DEAD"得出；`UNKNOWN` 表示"探测或枚举无法得出结论"（含 EPERM、工具失败、枚举不可得），**与 ALIVE 同等严格**；`ALIVE` 表示至少一个被观测到的进程仍在。禁止 `catch => false`，禁止部分答案取整为 `DEAD`。 |
| **quiescence 最终语义** | `quiesced_at` 只表示"这条命令的执行槽位可以复用"，且只有三种证明可以写：`closure.v1`（上下文已关闭）、`startup-failed.v1`（从未打开）、`no-progress.v1` **且 `process_tree === 'DEAD'`**。它**不**表示浏览器环境可以交还。 |
| **environment release 最终门槛** | `releaseQuarantine`：action 终局（`VERIFIED_SUCCEEDED` / `VERIFIED_FAILED` / `NEEDS_HUMAN`）→ 无提交意图（NEEDS_HUMAN + 已提交 ⇒ `SUBMISSION_UNCERTAIN`）→ 无 pending 命令 → **每条已 quiesce 的命令都有且仅有一条 `closure.v1` / `startup-failed.v1` 证明** → 资源不被他人占用 → 才 `state='IDLE'`。终止证明（哪怕 tree `DEAD`）**永不**放行。 |
| **weak→strong 升级规则** | `PROVEN_CLOSED`(3) > `NEVER_OPENED`(2) > `PROCESS_ONLY`(1)：强可替换弱；弱不得替换强；同强度同实质 = 幂等（返回磁盘那份）；同强度不同实质 = `IDEMPOTENCY_CONFLICT`；`.tmp` 按 kind 分离；写入走独占创建（`linkSync`→EEXIST→`renameSync` 回退）并重试 4 次。 |
| **retention 后 safety fact 是否仍保留** | **保留**。retention 只拥有页面载荷与终局结论；`termination` 与 `GUARDIAN_NO_PROGRESS` 从 closure 记录读取并原样带过（含"从未收到回执、由记录合成回执"的那条路径）。端到端证据见 §3 P1-03。 |
| **Windows taskkill deadline 证明** | ① `runToolWithDeadline` 用真实 60s 睡眠进程验证 400ms deadline 下返回 `TIMEOUT`，且总耗时 < 10s；② 真实 `taskkill` 在 1ms deadline 下 `TIMEOUT`；③ `terminateProcessTree(pid, {deadlineMs: 2})` 在 < 2s 内返回，`tool:'TIMEOUT'`、`enumeration:'UNAVAILABLE'`、`process_tree:'UNKNOWN'`，且**被测进程仍存活**（没杀成就不许声称杀成）；④ `terminate()` 把整段强制阶段压在 `policy.force` 内（终止调用 ≤ force/2，其后等待 ≤ 剩余）。诚实边界：探测（`kill(pid,0)`）本身是同步且 O(1)，理论上可在预算之外多花极少时间；未观测到超预算的实例。 |

## 6. 新发现问题与 follow-up ledger（§八-21 / §八-22）

### 6.1 本轮新发现并**已修复**

**NEW-B012-01：`recoverExpired` 在"action 已被回执判定终局"时抛出，导致整轮 recovery 中断、命令与槽位永久无法过期。**
- 触发：命令被 claim → 报告被接受（action 进入 `BLOCKED` 等终局态）→ 租约随后过期 → `recoverExpired` 对已终局 action 调 `assertTransition(终局, NEEDS_HUMAN)` ⇒ `VERSION_CONFLICT`，异常冒泡中断整轮 sweep。
- 影响：这是"执行槽位永久占用"的第二条路径（B01.1 修掉的是第一条：promise 永不 settle）。
- 修复：`decided` 判定——action 已是终局时，recovery **只**回收命令与租约，不重写 action 的状态、错误码与成本记录（回执已经决定了它的命运）。
- 证据：集成用例在本轮第一次跑出该组合（原 `packages/core/src/execution.ts:239` 抛出），修复后通过。

**NEW-B012-02：证据写入的"清理临时文件"失败会中止 `saveEvidence` 的重试循环，使**已证明的 closure 输给 weak 记录**（`guardian-protocol.ts`，BASE 已存在）。**

- 发现过程：交付前的冻结工作树首跑，`tests/unit/guardian-evidence-upgrade.test.ts > keeps the weak writer from displacing a closure written at the same time` 在全量单测负载下失败（`expected 'GUARDIAN_UNCONFIRMED' to be 'kff.guardian-closure.v1'`）。只跑该文件 4/4 通过，说明它依赖一个窄时序——但不是"测试在负载下抖动"，而是一条真实缺陷。
- 复现（独立、可重复，见 §5 证据）：让真实 `guardian-child` 走完它的真实生命周期，同时按 5ms 节奏并发写 weak 记录（与用例同一手法），4 次里稳定复现 1 次：
  - 子进程 `exit code=1`（`guardian-child.ts:126` 的 `catch { process.exit(1) }` 吞掉了错误）
  - 目录里留下 `<command_id>.json.closure.tmp`，**453 字节 —— 与成功发布的记录同样大小**（写入本身成功了）
  - 最终文件仍是 weak 的 no-progress 记录
- 机制：`writeEvidenceFile` 的 `finally { if (existsSync(tmp)) unlinkSync(tmp) }`。独占创建输掉竞争时该函数 `return false`（设计如此，交给 `saveEvidence` 重试）；但只要这次**清理**抛出（Windows 上刚写入/刚被 rename 覆盖的文件常被扫描器短暂持有），异常会顶掉 `return false`，一路冒泡出 `saveEvidence` —— 于是**还剩 3 次重试的写入被放弃**。weak 记录因此留在盘上，strong 写入者退化为"没有证明"。
- 影响：**不是安全漏洞，是可用性缺陷**。结果仍是 fail-closed（父进程 `readClosure` 拒绝非 closure 记录 ⇒ `GUARDIAN_UNCONFIRMED` ⇒ 环境保持 `QUARANTINED`、需人工），但**一条已经写成的真实 closure 证明被丢弃**，而这正是 P1-01 第 5/6 子项要保证"strong closure 能安全升级 weak evidence、两个 writer 不再争同一个 proof file"的地方。
- 修复（+35 行含注释）：① `withTransientRetry`（Windows 瞬态拒绝的有界重试，`EPERM/EACCES/EBUSY/EMFILE/ENFILE`，与 `scripts/local-runtime-state.ts` 的 `saveRuntimeJson` 同法同码）；② `removeTemp`（清理是"清理"不是"决定"：失败不抛出，最多留一个无害的临时文件，由下一个同 kind 的写入者清掉）。**永久性拒绝仍然抛错**，没有把失败伪装成成功。
- 证据：修复前 10 次复现中失败 2 次；修复后 16/16 全部得到 `kff.guardian-closure.v1` 且无残留 `.tmp`；全量单测 19 文件全绿。
- **缺口（必须如实记录）**：这条瞬态路径**没有确定性回归测试**——要确定性地制造一次"rename/unlink 被拒绝"需要可注入的 fs 故障层（本机唯一可构造的确定性故障是 EISDIR/EACCES 的永久形态，走的是另一条分支）。列入下一轮：可注入 fs 层的确定性回归。

### 6.3 被标记的范围决定（P2-05 一行改动）

规划端 §二 把 P2-05 列为"记录即可，除非 P1 的修复无法在不碰它的情况下保证统一终局不变量"。

`onSpawn()` 抛错时，BASE 的代码是 `child.disconnect(); reject(error)`——**直接 reject，不经过 `settle()`**。本轮 P1-01 的硬要求是"settle 之后所有 IPC 消息路径必须失效"，而 `settle()` 正是摘监听 + 断通道 + 一次性终局的那道闸门。若这条路径继续绕过 `settle()`，那么"已终局"与"通道已关"之间就存在一个不由 `settle()` 管辖的缺口，P1-01 的不变量在该路径上不成立。因此本轮把它改成 `settle(() => reject(error))`（**一行**，不改变对调用方的可见行为：仍然是同一个 error 拒绝）。

**这不是顺手重构**，但它确实触碰了一个被规划端标为"仅记录"的条目，因此按 §二 的要求在此**先行报告**，并给出回退选项：若规划端认为应保持 BASE 行为，可只回退这一行，代价是 `onSpawn` 抛错路径重新回到"不由统一 settle 管辖"的状态。
