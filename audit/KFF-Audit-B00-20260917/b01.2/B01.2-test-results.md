### 5.2 全量集成末跑：`418 passed / 2 failed`——**负载下枚举超时，树降级为 UNKNOWN**

改写断言之后，同一个文件**单独跑通过**（`browser-message-exit=0`，§4.5），**39 worker 并发跑失败**（§4.6，原文见 `b01.2-full-integration-fail.log`）。同代码、同文件、同冻结工作树，差别只有机器负载，所以这是负载相关的，不是逻辑回归。

失败形状（两条完全同形）：

```
 termination: {
   descendants: "DEAD",
   elapsed_ms: 1736,          // 另一条 1767
-  enumeration: "LISTED",     +  enumeration: "UNAVAILABLE",
-  process_tree: "DEAD",      +  process_tree: "UNKNOWN",
   root: "DEAD",
   sampled: 0,
   tool: "SUCCESS",
 }
```

**机制已实测，不是推测**（`b01.2-enumeration-under-load.log`，诊断脚本，非交付测试）：

| 条件 | 结果 |
| --- | --- |
| 空载 / 2500ms deadline | **12/12 成功**，中位 815ms，342 行 |
| 24 个满载进程 / 2500ms | **12/12 超时**，`bytes=0`（被杀时一个字节都没输出） |
| 24 个满载进程 / 5000ms | **6/12 成功**，中位 5012ms（全部贴着 deadline） |

失败分支是 `TIMEOUT`（不是 spawn error、不是非零退出、不是空输出），`listProcesses` 把它折叠成 `null` ⇒ `enumeration='UNAVAILABLE'` ⇒ `treeStateFrom` 判 `UNKNOWN`。

**关键算术（容易看错）**：失败记录里 `elapsed_ms` 只有 1736ms，看似没超预算，但那两条用例传的是 `liveness.force = 5000` ⇒ `budget = force/2 = 2500ms` ⇒ `enumerateMs = min(5000, 2500/2) = `**`1250ms`**。枚举在 1250ms 被杀，剩余预算才轮到 `taskkill`。**枚举份额 = force/4**。

**并且这不是"测试预算太小"而已**：生产默认 `force = 10000` ⇒ 枚举份额 2500ms，而负载下 2500ms 是 **0/12**。生产路径在机器繁忙时同样会落到 `UNKNOWN`。

**行为是否正确**：正确。§三 已裁定 tree `UNKNOWN` ⇒ fail-closed，不得形成 execution quiescence proof，环境保持 `QUARANTINED`。生产就是这样做的：`acceptReport` 不写 DONE、`recordQuiescence` 拒收、环境保持隔离。**这是 fail-closed 的运营代价，不是安全回归。**

**为什么不能靠改断言解决**：这两条用例下游断言 `agent_commands.state='DONE'` 且 `quiesced_at IS NOT NULL`，而这两条**只有在 `process_tree='DEAD'` 时才可能成立**。改成宽松匹配，测试会在下游同一个事实上以另一种方式失败——问题不在断言，在于"这次枚举没成功"。

**本轮不改生产、不改测试预算**（§七：新发现先记录证据、影响与最小修复方向，不自行扩大范围）。已升级 LEDGER-NEW-08，并在交付报告里列为复审第一项。

## 7. `context-opened` 晚到（§五 第 5 项）：未覆盖，原因与现状

子进程只有在真实 `BrowserContext` 打开之后才会发 `context-opened`，而每一条 settle 路径要么杀掉子进程、要么断开 IPC 通道，所以"settle 之后到达的 `context-opened`"在当前架构下**无法**用单测或集成测安排出来。本轮的做法是把它变成**结构性**保证：

```ts
const settle = (body) => { …; child.off('message', onMessage); try { if (child.connected) child.disconnect(); } catch {} ; decide(); };
async function onMessage(message) { if (settled) return; … }
```

两处都成立时，settle 之后到达的**任何** IPC 消息（`ready` / `context-opened` / `before-submit`）都不可能再触达命令状态。第 4、6、7 项用 `ready` 与 `before-submit` 端到端证明了这个机制；`context-opened` 走的是**同一个** `onMessage`，因此被同一个断点覆盖——但这是推理，不是观测。**列入下一轮验收项（浏览器级），不得写成 PASS。**
