# KFF Stripe 退款与调整

依据规划 7.7、TASK-095、ACC-29 退款子范围及 ADR-019。KFF 使用自己的原始付款凭据、客户和订单，支持同一付款的部分/多次退款、处理中、补充操作、失败、取消、争议和独立账目调整。Stripe 实际账号与密钥配置按用户要求后置；本文说明已实现的代码合同，未将本地合成结果视为实际商户验收。

## 订单页面与权限

在已核实的订单付款下展开“退款与调整”。先核对原付款，页面显示已核实退款净额、剩余可退额度、本地预占与退款后收款余额。管理员填写原币种金额、处理依据与退款原因，勾选确认后保存退款申请；操作员和查看者不能发起退款或账目调整。页面只接受十进制金额，服务器使用整数最小单位计算。

连接的“暂停新收退款”、品牌停止与组织停止会阻止新的外部创建。已发出的退款继续只读核对；已经到达 Stripe 的请求无法由本地停止撤回。申请人的管理员权限在提交前重新检查。LIVE 创建还要求服务端显式启用；TEST 的付款、退款与调整始终标注为测试，不能计作真实收入。

仅未提交且没有提供方对象的 READY/NEEDS_HUMAN 申请可以填写原因撤销。已经提交但结果未知的申请不能当作未发生来取消，也不能释放额度另开一笔。页面提供“核对原退款与争议”，只请求原对象核验，不重新授权 NEEDS_HUMAN 退款。

## API

除已存在的原始 Stripe 签名端点外，所有接口需要运营登录、服务端品牌作用域及写入同源校验。请求严格拒绝多余字段，不接受浏览器指定品牌、提供方对象、私钥或成功结果。

| 接口 | 合同 |
| --- | --- |
| `GET /api/payments/:id/financials` | 本品牌已核实付款的财务概览及最近 100 条各类明细；汇总计算所有记录 |
| `POST /api/payments/:id/refunds` | 管理员确认 `request_id`、`expected_version`、`amount_minor`、`confirmed_available_minor`、`reason`、可空 `provider_reason` 与 `REFUND_CONFIRMED_AMOUNT`；持久排队返回 202 |
| `POST /api/payments/:id/financial-recheck` | 操作员或管理员填写请求 ID、原因，重新安排原财务对象查询，返回 202 |
| `POST /api/refunds/:id/cancel` | 管理员按当前账本版本与原因撤销尚未提交的申请 |
| `POST /api/payments/:id/adjustments` | 管理员填写原币种整数金额、DEBIT/CREDIT、唯一依据、原因、可空关联争议 ID、当前版本与 `RECORD_ACCOUNTING_ADJUSTMENT` |
| `POST /api/adjustments/:id/reverse` | 管理员填写请求 ID、当前账本版本、原因、新依据标识与 `REVERSE_THIS_ADJUSTMENT`，添加一次相反调整 |
| `POST /api/stripe/webhooks/:connection_id` | 共用原始字节验签与持久收件；退款/争议事件只触发服务器核验 |

人工调整不调用 Stripe，也不改变退款额度或交付状态。其金额、原币种/精度、证据与操作者不可修改；冲销与原记录关联，不能重复冲销或冲销反向条目。同一付款不能重复使用相同依据标识，重放原请求则返回原结果。

## 额度、状态和资金记录

每个已核实付款自动建立一份独立退款账本，现有付款在迁移中补齐。数据库以组织/品牌 RLS、复合外键和只读历史约束边界。

- 可退额度 = 原已核实付款 − 提供方占用 − 尚未绑定提供方对象的本地申请预占，显示值最低为零。未知结果继续预占。
- 提供方占用包含 pending、requires_action、succeeded 和未知状态的退款；与原 Charge 已退款金额取较大值，不能靠遗漏的已知对象释放额度。failed/canceled 经查询核实后释放其占用。
- 退款净额由不可变资金条目计算。当前成功退款记负向变动；成功后转回 requires_action/pending 或变成 failed/canceled 时，添加相反变动。之后再次成功可以产生新的观察及负向条目。未知新状态保留原资金结果与占用，暂停新退款。
- 退款后收款余额 = 原付款 − 已核实退款净额。含人工调整的账目金额在此基础上加入已确认的有符号调整；不是 Stripe 最终结算额。
- 争议状态和实际余额变动独立保存，余额条目按提供方交易 ID 去重，保留实际币种、金额、费用、净额。不会猜测换汇，或自动将不同币种争议/费用冲入原付款；按明确证据需要记录的调整另行关联。

申请时锁定账本并核对版本、页面确认的可退额与 15 分钟内的完整核验结果。执行者在真正提交前再次查询提供方并复核额度，不能使用扣除自身之前被截断为零的展示余额来放大可退款金额。Stripe 仍按实际账户状态决定受理，外部后台可同时变化；API 拒绝或未知结果保留明确状态供核对。

## 持久队列、签名事件和恢复

退款固定原 PaymentIntent、金额、原因及四个 KFF 元数据关联，使用 `kff-refund-<退款申请 UUID>` 幂等键。首次提交时间与原参数不可改写。首次明确的创建请求拒绝才可据此标记 FAILED；创建后查询错误或此前已有未知提交不能证明未创建。

每个付款持有 90 秒财务租约，分页及查询间续租，旧 token 或过期结果不能提交。执行者查询原 PaymentIntent（展开最新 Charge），逐项检查金额、到账额、币种、模式、商户及 KFF 订单/快照元数据。退款和争议按原 PaymentIntent 分页查询，100 项一页、最多 100 页；分页循环、超过上限、无法读取已知对象或身份不符会停止核验，保留原记录。

所有已知退款/争议对象及触发事件对象即使未出现在列表里也按原 ID 查询。收到创建结果后先持久绑定退款 ID，再做后续完整核验。未知提交在首次提交后 23 小时内只使用原键/原参数；超过窗口不再重发，保留预占并进入人工处理。若之后查询找到了原对象，可按证据恢复状态。

原始 Webhook 的签名、512 KiB 上限、300 秒时间窗口、API 版本、商户/模式限制与收款共用。事件及共用入站记录提交后才确认；事件重放不重复落库，相同事件 ID 变更内容会被拒绝。Refund 对象本身没有 livemode，模式依据已验签事件及原付款/Charge核对。

回调不是当前退款状态的最终来源：始终查询提供方当前对象，避免旧成功/失败事件覆盖后来的处理结果。付款财务租约和事件租约同时有效，退款/争议观察、当前投影、资金条目和事件完成同事务提交。未找到 KFF 已核实原付款的事件保留为 IGNORED 并说明原因；后续形成付款凭据会自动建立完整核验账本，查询已有退款/争议。

普通 Worker 默认跳过本地合成连接。暂时错误指数退避，最多 8 次后保留人工核对；组织/品牌/连接暂停时保留申请并定期检查。按需核对可以重新安排读取，不能把未知退款变成一笔新申请。长期运行、网络环境和真实提供方恢复行为仍须在实际测试商户验证。

## 后续配置与验证边界

配置动作已由用户明确后置，此处是恢复联调时的合同说明。沿用 [Stripe 支付配置](stripe-payments.md)，Restricted API key 还需允许 Refunds 创建/读取、Disputes 读取及原 PaymentIntent/展开 Charge 读取；只授予所用商户必要权限。没有 Connect、争议关闭或争议证据提交调用。

在原支付事件之外订阅 `refund.created`、`refund.updated`、`refund.failed`、`charge.refunded`、`charge.dispute.created`、`charge.dispute.updated`、`charge.dispute.closed`、`charge.dispute.funds_withdrawn`、`charge.dispute.funds_reinstated`。继续使用已安装 `stripe@22.6.2` 与 `2026-08-26.dahlia`，Web 和 Worker 使用相同私密绑定。

本地覆盖真实 SDK 对本地 HTTP 服务器的编码、数据库原子性与恢复、实际 Worker 进程终止后恢复、回调故障、角色/品牌边界、桌面/手机页面与独立端口生产构建。未配置实际 Stripe 商户、未产生真实收退款、未创建外部端点；实际失败/争议样例、资金到账和生产网络验收待后置联调。交付失败恢复由 TASK-096 实现，当前不计完整 ACC-29 通过。

回滚时先暂停新收退款，保留原请求、占用、已应用迁移及查询能力。纠错用新迁移或新的证据记录；不能删除未知申请、篡改不可变资金条目或回退已核实付款。
