# 本机数据库恢复与升级验证

本机验证支持 PostgreSQL 17、Windows x64。它在新的目录和端口启动备份副本，不替换当前数据库，也不启动副本的 Worker 或 Agent。

核对已有备份能否恢复，使用 `--restore-only`：

```powershell
pnpm db:verify-backup .kff/backups/before-owned-coldstart-20260913T104811500 --restore-only
```

此模式不执行迁移。它在只读事务中读取全部 KFF 表，核对已应用迁移的源码摘要，记录每张表的行数、SHA-256 及 RLS 标志；尚未应用的迁移只列在报告中。为核对运行库前后是否一致，只排除 `agents.heartbeat_at`，其余字段完整比较。恢复副本的表摘要可与备份时的清单独立比较，不能仅凭副本能启动就认定记录完整。

报告写入 `.kff/checks/backup-restore-UUID.json`。成功必须同时满足读取完成、副本确认关闭、运行库前后摘要一致。副本保留供复查；这不是覆盖运行库的恢复按钮。

2026-09-13 实测：上述备份18,191个文件在复制前后SHA-256全部匹配，恢复的92张表、10,165条记录与停库时摘要一致；31条迁移和RLS标志匹配，未执行迁移。副本正常关闭，运行库、配对与176个Agent文件保留。损坏摘要、运行PID标记和错误参数均在复制/启动前被拒绝。类型、相关代码检查、生产构建和恢复后的工作台页面通过，见 [实测证据](../evidence/database-restore-latest.json)。

以下为此前特定 **27→28** 版本的升级验证。在与第28条迁移配套的源码版本下，不带该选项才执行原 `scripts/migrate.ts`；当前已有31条迁移的源码不能将这项历史验收扩展为任意升级路径。

```powershell
pnpm db:verify-backup .kff/backups/before-browser-message-20260913-015620
```

备份目录必须在本工程 `.kff/backups` 内，包含完整 `postgres` 目录、`manifest.json` 和原 `local-config.json`。需要保留其隐私，不能放入程序发布包。清单列出每个文件的相对路径、字节数和 SHA-256；脚本拒绝目录链接、漏项、重复路径、摘要不符和包含运行PID的备份。文件系统备份要求关闭数据库后复制完整集群，依据见 [PostgreSQL 17 文档](https://www.postgresql.org/docs/17/backup-file.html)。

脚本创建新的 `.kff/restore-checks/UUID/postgres`，再次核对所有副本文件，分配独立本机端口并检查数据库实际目录。它不会把数据库密码输出到报告或命令行。现有代码目录保持不动，故障探针只修改副本旁的迁移文件。

验证依次执行：

1. 让待执行迁移在新增字段后故意报错，确认原事务回滚、历史未增加、数据未改变。
2. 使用当前正式迁移文件完成升级，核对既有数据、原迁移历史和所有迁移摘要。已有 Facebook 连接保持 API 默认通道。
3. 再执行一次迁移，确认历史时间戳和数据不变；修改已执行过的迁移副本，确认校验拒绝且不改变数据。
4. 检查相关6张表仍启用RLS，消息校验触发器仍以调用者权限运行。
5. 关闭副本并确认其终止状态，比较运行库中账号、线索、客户、会话、消息与移交记录的前后摘要。

报告写入 `.kff/checks/backup-upgrade-UUID.json`。`complete=true` 必须同时有 `restored_server_closed=true`；报告保留文件摘要、迁移记录和数据内容摘要，不输出行内容。升级比较覆盖所有既有业务表，忽略本次新增的 `facebook_connections.transport` 列后核对旧字段；迁移历史另行核对。副本保留以供复查，不自动删除。

此验证证明指定27→28迁移在本机真实旧备份上的结果，不能推广到未测版本、另一主版本 PostgreSQL、跨机器安装或任意Agent日志版本回退。当前不提供一键覆盖运行库的恢复操作；程序回退也不能通过删除日志或占用锁代替关闭证明。
