# ADR-020：第一阶段聚焦 Facebook → WhatsApp

2026-09-12，当前用户目标覆盖此前“退款后暂停”和“第一阶段 Stripe”的开发优先级。KFF 继续独立拥有客户、身份、消息、执行记录和数据；不连接其他项目主数据。

第一阶段为 Facebook 互动/私信 → 客户建档与来源 → 意图识别与基础接待 → 人工接管 → WhatsApp 邀请 → 销售确认及统计。AI 不报价、收款、交付或成交；后续由现有销售团队在 WhatsApp 处理。已有订单、支付、退款功能冻结保留，不删除，不作为引流开发的门槛。

接待复用原 Customer/Identity/Conversation/Message/Event 和 Task/Action/Job/Agent/Lease/guardian，不引入第二套 CRM 或执行调度。原表不足之处通过第 18–21 个增量迁移扩展；历史迁移和原始规划不改写。WhatsApp 只保存目的地号码、话术快照和邀请证据，不接 WhatsApp API。

采用账号/渠道/远端标识去重，评论身份与 Messenger PSID 不凭同名合并。首个观察来源不可变；平台缺失的来源保持未知。发送快照固定账号、客户、最近消息、控制版本、停止 epoch、联系依据和目的地版本。

自动接待准备使用原 jobs 的 RECEPTION 类型。Worker 租约带 fencing token，超时可接手，失效判断不生成发送；外部模型最多三次失败后转人工。接管增大会话版本，已经授予提交意图的动作只能继续核验，不能声称撤回。发送过程复用既有提交门槛与单槽 Agent；未知结果不自动重发。

本地规则明确标为预演；可配置模型接口提供结构化建议，由业务层约束动作、次数、服务窗口、号码和停止行为。明确退订在收件事务内立即生效。真实 Facebook、真实模型效果和生产平台放行保留独立证据边界；本地成功不自动提升真实能力。

验收与当前状态见 [40 项审计](../kff-lead-generation-status.md)，操作说明见 [Facebook 引流 API](../api/facebook-leads.md)。高级运营、批量增强等 P2 后置。
