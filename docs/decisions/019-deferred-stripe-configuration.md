# ADR 019：Stripe 实际配置后置，完成后通知

用户明确要求“这个先不配置，继续下一个”。因此 Stripe 测试商户与密钥配置、实际网络联调后置，继续按规划 TASK-095 退款与调整及后续可独立实施的代码。沿用已选择的 Stripe 协议和本地合成测试，不把配置缺口当成继续编码的阻塞，也不将本地结果记为实际商户验收。

用户同时将总目标的结束动作改为“把文件都保存好，通知我”。这替代此前的关机要求；后续完成时保存并通知，不执行或安排关机。原规划内容、未完成范围和遇到无法确定的问题时暂停询问的要求继续有效。

用户随后明确“这个退款部分做完可以暂停了”。本次范围因此收在 TASK-095：完成退款与调整代码、验证和保存后暂停，不继续 TASK-096 或其他后续任务。暂停是用户指定的阶段终点，不表示完整项目已交付。

TASK-095 使用同一品牌、原支付凭据、共用入站事件和审计。退款授权由管理员在形成原支付、明确金额、可退额度与依据后一次确认。队列持久预占额度；提交前查询原 PaymentIntent、Charge、完整退款和争议列表，再复核额度、授权与停止状态。同一未知请求在安全窗口内复用原幂等键，不能另建退款猜测重做。

每笔原支付使用一个有 token 的财务核验租约，串行处理当前提供方状态；旧租约不能写入。回调只触发原支付对象的服务器核验，不直接将旧回调状态覆盖当前状态。退款当前状态、不可变观察记录和资金变动分开保存；成功后返回 requires_action 或后续失败时记录反向变动，保留原始成功证据和处理中的额度。

争议及其提供方余额变动单独保存，保留实际币种，不猜测换汇或手续费。人工指定的账目调整独立记录依据、金额及操作者，纠错用关联反向条目，不改写付款或退款事实。退款与调整均不改变交付状态。

协议依据：[Refund 创建](https://docs.stripe.com/api/refunds/create)、[Refund 对象](https://docs.stripe.com/api/refunds/object)、[Refund 分页](https://docs.stripe.com/api/refunds/list)、[退款状态及事件](https://docs.stripe.com/refunds)、[Dispute 对象](https://docs.stripe.com/api/disputes/object)、[Dispute 分页](https://docs.stripe.com/api/disputes/list)。SDK 继续采用已核对的 `stripe@22.6.2` / `2026-08-26.dahlia`。
